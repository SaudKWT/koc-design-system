# Consumer report — two accessibility defects in `@koc/*`

Found by running Playwright + axe over the DWOS app's five real screens, at
`v0.1.2`. Both are assembly-visible only: they need a composed page to appear, so
the docs app's own suite would not surface them.

Neither is fixed on the consumer side, deliberately — editing an installed
component means the next `koc:add` silently reverts it. They are scoped out of
the app's suite instead, in a way that keeps guarding the app's own content, and
the scoping is annotated to be deleted when fixes land.

---

## 1. `@koc/app-shell` renders the sidebar outside any landmark

**Rule:** `region` (moderate) · **19 nodes** on a typical screen.

The shell produces `main` (via `SidebarInset`) and two `header`s. The sidebar —
every nav link, every group label, the unit switcher, the user menu — is in
neither, and there is no `nav` around it. Measured in the app:

```js
landmarks:        ["main sidebar-inset", "header", "header", "nav breadcrumb"]
sidebarInsideNav: false
```

The only `nav` on the page is the breadcrumb.

**Consequences beyond the axe rule.** Screen-reader users lose landmark
navigation to the primary nav, which is the normal way to reach it without
tabbing through the page. It also breaks the obvious test selector: our first
attempt used `getByRole('navigation').getByRole('link')` and found 3 links — the
breadcrumb's — instead of the sidebar's. Any consumer writing that test will hit
the same thing and may conclude their nav is broken.

**Suggested fix:** wrap the sidebar's content in `<nav aria-label="…">`, or set
`role="navigation"` on the existing container. The label matters because the
breadcrumb is also a `nav`; two unlabelled ones are worse than one.

**How we scoped it:** `AxeBuilder().exclude('[data-slot="sidebar"]')` for the
`region` rule only, so the rule still fails on content the app owns. Matching on
the selector text did not work — axe names some nodes `a[href$="ddr"] > span`,
with no mention of the sidebar, so subtree exclusion is the reliable mechanism.

## 2. `@koc/alert` hardcodes `<h5>` for `AlertTitle`

**Rule:** `heading-order` (moderate).

```tsx
const AlertTitle = React.forwardRef<HTMLHeadingElement, …>(
  ({ className, ...props }, ref) => (
    <h5 … />
  ),
);
```

A page with an `h1` from `PageHeader` and an alert in its body goes `h1 → h5`.
That is not an edge case: it is the shape of every page that uses both, and we
hit it on two of five screens immediately.

```
/          H1 "Drilling & Workover Operational Support"   H5 "Vessel Movement lives under…"
/unit-1/npt H1 "NPT tracking"                              H5 "This screen has not been built"
```

**Suggested fix:** render a `div` — which is what shadcn canonical does now — or
take a `level` / `as` prop. An alert's title is rarely a document heading; when it
is, the page knows what level it should be and the component does not.

**Worth noting while you are in there:** the component deliberately does *not*
set `role="alert"`, and the comment explaining why is good — `role="alert"` is
for messages that appear in response to an action. But it means `AlertTitle` is
an `h5` inside nothing identifiable, so a consumer writing "ignore headings that
are alert titles" has to match `[data-slot="alert"]`. That works; it is just not
the first thing anyone reaches for.

**How we scoped it:** exempted at rule level, plus a guard test asserting the app
has no `h5`/`h6` outside `[data-slot="alert"]`. Without that guard the exemption
would hide the app's own heading mistakes, which is the usual way an allowlist
rots.

## Not defects — for context on what the suite covers

Four other defects turned up in the same run and were all **ours**, fixed here:
a `Field` wrapper that lost its implicit label association in the port to
`@koc/label` (eight unlabelled controls on the report form), three controls
carrying only a `title`, and a full-bleed map screen with no heading at all.

That ratio is the useful signal: four app faults to two component faults. The
components are in good shape; what neither repo was checking is **composition**,
and that can only be checked from here.

The suite is `web/tests/a11y.spec.ts` in the DWOS platform, ~170 lines, Chromium
only. It is not a screen-reader test and says so in its header — NVDA + Edge on
Windows remains undone and is recorded as such in that repo's handoff.
