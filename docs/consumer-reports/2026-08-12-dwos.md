# Consumer report — DWOS platform, 2026-08-12

From the first real consumer (`SaudKWT/dwos-platform`, `web/`), pinned at
`v0.1.2`. Everything below was measured in a built app, not inferred.

Why these reports exist: this monorepo is structurally blind to a whole class of
bug. `apps/docs` imports `packages/tokens/dist/koc-tokens.css` by relative path,
so it always receives the entire generated stylesheet and cannot fail the way a
registry consumer fails. Every distribution gap so far — the missing `@theme`
scales, the missing base layer and `@utility` rules, the type scale, the bare
`transition-all` — was found from outside. `check:parity` closes most of that for
the theme. It says nothing about the components.

---

## Confirmed: the type scale, with a bigger blast radius than stated

Before `v0.1.2`, in the running app, both classes computed to exactly the size of
a `<div>` with no class at all:

```
text-2xs  14px      text-md  14px      (no class)  14px
```

After re-adding at `v0.1.2`:

```
text-2xs   14px → 11px
text-md    14px → 16px
text-sm    14px → 13px
```

**That third line needs to be in the release note.** The finding was described as
affecting badges, timestamps and `size="lg"` buttons. But KOC's `--text-sm` is
`0.8125rem` where Tailwind's default is `0.875rem`, and `--text-base` is
`0.875rem` against Tailwind's `1rem`. So this is not only the two dead classes —
**every `text-sm` and `text-base` in a consuming app moves on upgrade.** Here
that is most body copy, every table cell and every form label.

It is the right change. But a consumer going `v0.1.1 → v0.1.2` will watch their
whole app re-flow, and should be told to expect it rather than discover it. Now
documented in `CONSUMING.md` § *What changes when you upgrade the type scale*.

Breakpoints arrived correctly, `--breakpoint-3xl` included.

## 1. Two components do not compile under `noUnusedLocals`

`@koc/confirm-dialog` and `@koc/notification-menu` both
`import * as React from "react"` and never reference `React`.

`noUnusedLocals` is **on by default in Vite's `react-ts` template** and set
**nowhere in this monorepo**, so `tsc` cannot fail here and does fail in a
consumer. Same blind-spot shape as the theme and the type scale: a default in the
consumer's scaffold that this repo does not share.

Patched locally four times now; every re-add reinstates it. Two-line fix in
`packages/ui`. Left alone deliberately — that area is being actively worked.

**Worth considering:** turning `noUnusedLocals` on in the monorepo would make
this class of thing fail where it originates.

## 2. `popover.tsx` animates with no KOC easing

| component | easing named |
|---|---|
| `dialog`, `dropdown-menu`, `sheet` | `ease-in` |
| `navigation-menu`, `select`, `tooltip` | `ease-out` |
| **`popover`** | **none** |

`tw-animate-css` resolves the animation timing function from
`var(--tw-ease, ease)`, so popover's entrance runs on the browser's `ease` rather
than a KOC curve. Every sibling names one, which makes this look like an omission
rather than a decision.

`check:motion` misses it because it enforces easings on *transitions*, not on
*animations*. The rule, if the gate is extended: a class list containing
`animate-in` with no `ease-*`.

## 3. Cascade order is load-bearing and undocumented

`tw-animate-css` sets `animation` as a **shorthand**; `@utility duration-*` sets
`animation-duration` as a **longhand**.

It works — `animate-in fade-in-0 zoom-in-95 duration-slow` measures as
`animation: enter 0.24s` — but only because the `@utility` rules land later in
the cascade than the plugin's imported CSS. If that import order ever changes, or
the plugin is imported after the theme, every entrance animation silently reverts
to the shorthand's 150ms fallback and nothing errors.

Worth a sentence in `base-css.ts` beside the `@utility` block, since that is
where someone would go to change it.

## 4. `CONSUMING.md` § Updating was too thin — now fixed

Three CLI facts that cost real time, added in this commit:

- `--overwrite` is required to refresh an existing file; without it the CLI
  prompts and, in a script, stops with no error.
- One item per invocation. Many items in a single `shadcn add` join into one
  argument and 404. Verified with 36.
- **After a version bump, re-add everything, not just the theme.** This is what
  actually bit: after `v0.1.1` only `@koc/theme` was re-added, so twelve
  components sat on `v0.1.0` for a day carrying the bare transitions `716b007`
  had already fixed. `check:motion` against the installed copies reported 12
  problems; against `packages/ui` at the same tag, clean. Not a design-system
  bug — but the docs are what would have prevented it.

## 5. The vendored-registry path, and why it exists

The DWOS platform is a handoff deliverable: an in-house KOC developer deploys it
to KOC servers. The token setup in `CONSUMING.md` assumed `api.github.com` is
reachable and that the developer has a personal fine-grained token. Neither is a
safe assumption inside KOC, and `KOC_REGISTRY_TOKEN` was in fact never set on the
machine this app was built on — meaning **the documented GitHub path had never
been exercised by anyone**, and the KOC developer would have been the first to
try it.

So the registry is now vendored into the consuming repo, synced from a tag.

**Two forms that look like they should work, and do not** (both verified against
the current CLI on 2026-08-12):

- a relative registry path resolves against `https://ui.shadcn.com/r/`
- a `file://` URL returns *"not implemented... yet..."*

The workaround is serving `vendor/koc-registry/` over `127.0.0.1` for the length
of one command. That keeps the real CLI in the loop, so `registryDependencies`,
import rewriting and overwrite behaviour stay exactly as documented instead of
being reimplemented against the JSON.

Sync is `git show <tag>:apps/docs/public/r/*` into the consumer's `vendor/`,
never a working-tree copy, so an uncommitted experiment here cannot reach a
handoff. The consumer then receives a design-system change as a reviewable diff
in their own repo rather than a silent fetch — which is the better story when the
person deploying is not the person who changed the design system.

**What this asks of the design system:** tagging discipline. A vendored consumer
pins to tags, so anything not tagged is invisible to them. `v0.1.1` and `v0.1.2`
both exist for this reason.

Documented in `CONSUMING.md` § *No GitHub access? Vendor the registry*. The
working implementation is `web/scripts/koc-registry.mjs` and
`web/scripts/sync-registry.mjs` in the DWOS platform — copy those rather than
rewriting.

## 6. A component-level counterpart to `check:parity` — offered

`check:parity` covers the theme. The open question was whether a component could
still ship a class that only resolves because of something in this repo.

Built and run rather than eyeballed: take every class selector the consumer's
build actually emitted (1,013 across 245 utility families), then test every class
literal in the installed component sources against it. Anything in a known family
that emits no rule is dead in a consumer.

**Result: nine candidates, all nine false positives** — `select-content`,
`select-item`, `select-label`, `select-separator`, `select-scroll-up-button`,
`select-scroll-down-button` and `group-action` are `data-slot` values;
`aria-hidden` and `aria-pressed` are attribute names.

**No dead classes remain in the components.** The type scale was the last one.

The check needs both a built consumer stylesheet and the component sources, which
only coexist on the consumer side. It can live in the DWOS platform's build and
report failures upstream — say if that is wanted, or if this repo would rather
own it against a throwaway fixture app.
